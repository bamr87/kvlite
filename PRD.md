# Product Requirements Document (PRD): kvlite

> A small LSM-tree key-value store in Rust, growing into a Raft-replicated cluster.

Open work is tracked in [GitHub Issues](https://github.com/bamr87/kvlite/issues) and as `status: planned` entries in [features/features.yml](features/features.yml).

## 1. Overview

Learn storage engines and consensus by building them: a write-ahead log, memtable, SSTables and compaction, then Raft replication across nodes.

| Version | Date | Notes |
| --- | --- | --- |
| 0.1 | 2026-10-28 | Initial requirements and phased roadmap (repo foundation). |

## 2. Goals

- Durable single-node KV store (WAL + memtable + SSTables)
- Leveled compaction and bloom filters
- Raft-replicated multi-node mode with a gRPC API

Non-goals (near term): production hosting, paid services, anything outside the roadmap below without a PRD change.

## 3. Users

- The maintainer, learning rust ownership, traits and testing, lsm-tree internals by building.
- Fleet agents (hub evolution loop, backlog fan-out, `evolve` lane) that grow the repo one reviewed PR at a time.
- Fleet tie-in: A candidate embedded store for fleet tools (e.g. fleet activity log buffering) and a systems-depth showcase in the portfolio.

## 4. Requirements

Phases are the build order: an agent picks the earliest unserved requirement first.

### 4.1 Phase 1 — Foundation

- FR1: In-memory get/put/delete API with unit tests
- FR2: Write-ahead log with crash recovery

### 4.2 Phase 2 — Core

- FR3: SSTable flush and point lookups across levels
- FR4: Background compaction and bloom filters

### 4.3 Phase 3 — Fleet integration

- FR5: Raft leader election and log replication
- FR6: Network API (gRPC) and a CLI client

### 4.4 Non-functional

- NFR1: CI (`.github/workflows/ci.yml`, the fleet standard gate) passes on every PR.
- NFR2: No secrets or credentials are committed; configuration comes from environment variables.
- NFR3: Autonomous lanes are off by default, open pull requests only, and never merge.
